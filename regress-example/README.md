# Пример регресса прикладного решения

Образец того, как покрыть своё решение 1С регрессионными сценариями на навыке `web-test`: стенд
поднимается из эталонной базы, на неё накладываются актуальные исходники, решение публикуется под
ролями, сценарии проходят через веб-клиент, результат — отчёт Allure с историей.

Папка устроена как маленький проект: исходники решения в `src/`, набор регресса в `tests/app/`.
Набор переносится в ваш проект как есть — меняются настройки и сценарии, механизмы остаются.

> Агенту, который строит такой регресс для другого решения, — [BUILD-GUIDE.md](BUILD-GUIDE.md).

## Быстрый старт

Нужны: Windows, платформа 1С (путь — `v8path` в `tests/app/stand.config.json`), Node.js 18+,
Git, набор навыков с настроенным web-test (разовая установка — раздел Setup в `web-test/SKILL.md`);
для отчёта — Allure CLI (`allure-commandline`) в `PATH`. Apache при первом подъёме скачается сам.

Стенд вызывает навыки `db-*` и `web-*` через их `.ps1` в `powershell.exe`. Подходит любая сборка набора,
в том числе Python-сборка (`port-*-py`): `.ps1` в ней тоже есть. Вне Windows стенд сам не поднимется:
нужно заменить вызов в `resolveScript`/`execSkill` (`tests/app/_stand.mjs`) на `.py` через `python`
(параметры у портов те же) и поднять публикацию своим способом — `web-publish` рассчитан на Apache
под Windows (`httpd.exe`).

```bash
cd regress-example

node tests/app/_stand.mjs up                                     # поднять стенд (~1 мин с нуля)
node ../.claude/skills/web-test/scripts/run.mjs test tests/app/  # прогнать сценарии
node tests/app/allure.mjs run                                    # прогон со сбросом данных + отчёт
node tests/app/allure.mjs open                                   # открыть отчёт
node tests/app/_stand.mjs down                                   # погасить, освободить лицензии 1С
```

Раннер сам вызывает подготовку стенда перед прогоном, отдельный `up` нужен только для ручной работы.

## Что внутри

```
regress-example/            ← корень проекта
  src/cf/                   исходники решения (у вас — ваша типовая или своя конфигурация)
  src/cfe/Доработки/        расширение (у вас — ваши расширения, по папке на каждое)
  etalon/app.dt             эталон: база с данными, из которой поднимается стенд (+ манифест)
  seed/make-source.mjs      только для примера — синтезирует базу-источник эталона
  tests/app/                набор регресса — переносится в ваш проект
    stand.config.json       настройки стенда
    _stand.mjs              подготовка стенда: up / down / status
    _hooks.mjs              связка с раннером web-test
    webtest.config.mjs      контексты = пользователи (роли), пул лицензий, таймауты
    build-etalon.mjs        сборка эталона из рабочей базы
    allure.mjs              прогон + отчёт Allure
    _allure/                категории ошибок для отчёта
    00-smoke/, 01-…/        сценарии
```

Решение примера — заявка на расход с согласованием: инициатор создаёт и отправляет, согласующий
утверждает или отклоняет, утверждённую заявку менять нельзя; расширение требует комментарий к
заявке свыше 100 000; аудитор только смотрит.

## Сценарии: какой приём где

Каждый сценарий начинается с комментария: что проверяет, какой приём показывает, как сделать так же.

| Сценарий | Приём |
|---|---|
| `00-smoke/00-вход` | smoke: стенд жив, секундный тест первым |
| `01-согласование/01-отправка` | одна роль (`context`), шаги и проверки глазами пользователя |
| `01-согласование/02-утверждение` | процесс из нескольких ролей (`contexts`), передача номера документа между ролями |
| `01-согласование/03-запрет-правки` | проверка отказа: причина — из сообщений пользователю, данные — из эталона |
| `01-согласование/04-крупная-сумма` | табличный сценарий (`params`): граничные значения правила |
| `01-согласование/05-аудитор` | роль только для чтения; вход по `user` на публикации без пользователя |
| `01-согласование/06-отправка-по-статусу` | табличный сценарий по документам эталона |
| `01-согласование/_заявки.mjs` | общие шаги: когда выносить в хелпер, когда нет |

Сценарии написаны так, чтобы читаться как текст: участник назван по роли (`инициатор`,
`согласующий`), шаги — бизнес-действия (`открытьЗаявку`, `причинаОтказа`). Кириллица в
идентификаторах, именах папок и файлов работает со всей цепочкой — раннер, отчёт Allure, стенд;
латиница с такими же говорящими именами — равноправный вариант. Выберите одно для набора и
держитесь его.

## Как перенести в свой проект

1. Скопируйте `tests/app/` в `tests/<ваше-приложение>/` — файлы из git, без `.cache/`, `.artifacts/` и
   скриншотов ошибок. Корень проекта набор находит сам — два уровня вверх, поэтому раскладка
   `src/…` + `tests/<имя>/` должна совпадать.
2. Заполните `stand.config.json`:
   - `v8path` — `1cv8.exe` нужной платформы; `user` — пользователь с правом загрузки конфигурации
     (о пароле — «Пользователи и пароли»); `label` — имя стенда в вашем реестре `.v8-project.json`;
   - `cfSrc` — исходники конфигурации; `cfeSrc` — папка, в которой лежат папки расширений (не сама
     папка расширения); `standBase` — где создавать базу стенда;
   - `dtPath` — путь к эталону (см. ниже); `port` и `apachePath` — свой экземпляр Apache стенда;
   - `skillsRoots` — уберите: в обычном проекте навыки лежат в каталоге своей платформы
     (`.claude/skills`, `.cursor/skills`, `.codex/skills`, `.github/skills` и т.д.), стенд проверяет их все;
   - `publications` — по публикации на роль: `{ "appName": "app-sales", "user": "Менеджер" }`;
   - `extensions` — свойства подключения расширений по имени расширения (`Name` из его
     `Configuration.xml`, не имя папки), см. «Расширения».
3. Соберите эталон из рабочей или разведочной базы:
   `node tests/<имя>/build-etalon.mjs --source <база|.dt> --out <путь из dtPath>`.
4. `node tests/<имя>/_stand.mjs up`, затем пропишите контексты в `webtest.config.mjs` — по одному на
   публикацию, через `published('<appName>')`: порт и публикации он берёт из `stand.config.json`.
   Пишите сценарии — порядок разведки и дисциплина в `web-test/regress.md` каталога навыков вашей
   платформы (`.claude/skills/`, `.cursor/skills/` и т.д.).
5. Добавьте в `.gitignore` проекта:
   ```
   base/
   tools/
   .v8-project.json
   ConfigDumpInfo.xml
   *.dt
   tests/*/.cache/
   tests/*/.artifacts/
   ```

## Эталон и манифест

Стенд не собирает базу из исходников каждый раз: он восстанавливает эталон `.dt` (данные уже там) и
накладывает только то, что изменилось в исходниках с момента сборки эталона.

Рядом с эталоном лежит `<эталон>.manifest.json` — из каких исходников он собран:

```json
{ "cfHash": "…", "ext": { "Доработки": "…" }, "sourceCommit": "<коммит>", "builtAt": "…" }
```

- Совпадают исходники с манифестом — загрузка конфигурации и расширений пропускается.
- Изменились — грузится только разница `sourceCommit..HEAD` (`db-load-git`), если в `src/cf` нет
  незакоммиченного и HEAD — потомок `sourceCommit`; иначе (правки вне коммита, история переписана
  rebase или squash) — вся конфигурация. Расширения после загрузки конфигурации перегружаются
  всегда: загрузка может сбросить их привязку.
- Без манифеста стенд тоже работает, но первая загрузка идёт целиком.

`build-etalon.mjs` берёт данные источника (файловая база, `.dt` или серверная база
`--source-server/--source-ref`), накладывает текущие `src/cf` и расширения, выгружает `.dt` и пишет
манифест. На незакоммиченных исходниках он отказывается работать: манифест ссылается на коммит, и
правок вне коммита в эталоне не окажется (обход — `--allow-dirty`).

**Эталон в репозитории — исключение ради самодостаточности примера.** В своём проекте `.dt` в git не
кладите (размер, реальные данные, история): храните эталон и манифест вне репозитория
(`base/checkpoints/` под `.gitignore`) или в общем хранилище артефактов, путь — в `dtPath`.

Пересобирать эталон нужно, когда меняются данные, на которых идут сценарии, или базовая платформа;
правки исходников стенд накладывает поверх эталона сам. Эталон примера пересобирается так:

```bash
node seed/make-source.mjs                                              # база-источник примера
node tests/app/build-etalon.mjs --source base/source.dt --out etalon/app.dt
```

## Стадии стенда

| Стадия | Когда выполняется | Что делает |
|---|---|---|
| `restore` | базы нет или `--reload-data` | останавливает Apache, пересоздаёт базу из эталона, переносит отметки из манифеста |
| `config` | `src/cf` отличается от отметки или `--rebuild-config` | загружает изменения (`db-load-git`) или всю конфигурацию |
| `ext` | расширение изменилось, отработал `config` или `--rebuild-ext` | загружает расширение, выставляет его свойства |
| `publish` | публикация не отвечает или `--republish` | публикует под каждым пользователем из `publications`, засевает реестр |

Флаги пишутся после `--` у раннера (`run.mjs test tests/app/ -- --reload-data`) или прямо у `up`.
`--rebuild-stand` — всё сразу. Без изменений `up` занимает несколько секунд.

Отметки состояния лежат в `tests/app/.cache/stand/`. Отпечаток `src/cf` — дерево git плюс содержимое
незакоммиченных правок, поэтому правка уже изменённого файла тоже запускает загрузку.

`status` показывает базу, отметки и отвечают ли публикации; `down` гасит только Apache стенда — база и
публикации остаются, следующий `up` поднимает стенд за секунды.

## Пользователи и пароли

**Основной путь** — публикация под пользователем: `publications` в `stand.config.json`, по публикации
на роль. Адрес сам определяет, под кем вход, — удобно и для ручной проверки по ссылке.

**Альтернатива** — одна публикация без пользователя (`"user": null`) и пользователь у контекста в
`webtest.config.mjs`: `{ url, user: 'Аудитор', password: process.env.AUDITOR_PWD }`. Подходит, когда
состав пользователей меняется и перепубликовывать ради каждого неудобно. В примере так входит аудитор.

Пароли в `stand.config.json` и сценарии не пишут: файлы в репозитории. Стенд при первой публикации
засевает реестр `.v8-project.json` (в `.gitignore`) — записью на публикацию с пустым паролем; пароль
впишите туда, и следующий `up --republish` опубликует с ним. Существующие записи стенд не трогает.

**Пользователь стенда** (`user` в `stand.config.json`) грузит конфигурацию и расширения. Основной путь
— в эталоне у него нет пароля: стенд — одноразовая копия; если в исходной базе у администратора
пароль, заведите для загрузок служебного пользователя или снимите пароль на копии до сборки эталона.
Альтернатива, когда без пароля нельзя, — переменная `REGRESS_STAND_PASSWORD`. Дальше достаточно записи
в реестре: стенд засевает её на стадии публикации (у публикации под этим пользователем), но эта стадия
идёт после загрузок — поэтому на первом `up` пароль даёт только переменная.

## Расширения

Загрузка расширения из исходников включает ему безопасный режим, а в безопасном режиме платформа не
даёт перехватывать модули объектов: перехват молча не срабатывает, причина — только в журнале
регистрации («расширение модуля запрещено… подключено в безопасном режиме»). Поэтому свойства
подключения задаются в `stand.config.json` и выставляются после каждой загрузки:

```json
"extensions": { "Доработки": { "safeMode": "off" } }
```

Доступны `safeMode`, `unsafeActionProtection`, `active` (`on`/`off`). Свойства меняет `ibcmd`, ему нужна
монопольная блокировка — стенд сам останавливает Apache и поднимает публикации заново.

## Отчёт Allure

`allure.mjs run` — прогон всего набора со сбросом данных, результаты и HTML-отчёт в
`tests/app/.artifacts/` (переопределяется `REGRESS_ALLURE_DIR`). Каждый `run` чистит результаты, история
и тренды переносятся из прошлого отчёта — только с полных прогонов: срез (`--grep`/`--tags`) пишет в
отдельный каталог и тренд не трогает. В блоке Environment — платформа, версии решения и расширений,
эталон, публикации.

`_allure/categories.json` раскладывает падения по корзинам по тексту ошибки: «Заблокировано известным
дефектом (ожидаемо красный)» и «Инфраструктура стенда» (лицензии, вход, старт клиента, зависание).
В первую впишите тексты ошибок известных дефектов вместо заглушки: сами тесты о дефектах не знают,
после исправления текст перестанет совпадать, и тест просто позеленеет.

## Запуск из PowerShell 5.1 и CI

Имена тестов и шагов — по-русски, и вывод прогона в UTF-8. Windows PowerShell 5.1 по умолчанию
читает перехваченный вывод программ в кодировке консоли (cp866): в консоли всё видно, а в
`> лог`, `$вывод = node …` или `| Select-String` получится `╨Ъ╤А╤Г╨┐╨╜╨░╤П`. Перед запуском:

```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8
```

Для CI надёжнее не разбирать консоль, а читать отчёт из файла — `--report=<файл>.json`, JUnit или
Allure: они пишутся в UTF-8 и от консоли не зависят. Свои скрипты вокруг набора, которые работают с
путями (удаление, разбор вывода `git`), проверяйте на путях с кириллицей: например, `fs.rmSync` на
Windows такие пути молча не удаляет, а `git` выводит их экранированными без `-c core.quotePath=false`.

## Коды выхода и вердикты

| Код | Что значит |
|---|---|
| `0` | всё зелёное |
| `1` | есть красные — смотреть корзины и тренд отчёта |
| `2` | прогон упёрся в `--global-timeout` — проблема стенда, не тестов; отчёт частичный |
| `3` | зависло сворачивание прогона — проверить живые сеансы 1С и браузеры |
| `5` | выполнять нечего: фильтр не совпал ни с одним тестом или все выбранные пропущены (`skip`) |

Падение несёт вердикт: `hang` — заблокирован поток клиента, разбирать, что его подвесило; `slow` /
`slow-network` — всё живо, не уложились: поднимать `export const timeout` у теста; `browser-dead` —
окружение. Стартовые блокеры 1С (нет лицензии, отказ входа) движок распознаёт за секунды и называет
причину.

## Частые проблемы

- **Не удаётся удалить базу при `--reload-data`** — база занята: открыт сеанс Конфигуратора или
  Предприятия. Apache стенд останавливает сам.
- **«Не обнаружено свободной лицензии»** — сеансы держат лицензии: `_stand.mjs down`. Число
  одновременных сеансов ограничивает `maxContexts` в `webtest.config.mjs`.
- **Сменили `publications`, а входит прежний пользователь** — публикация отвечает по старым
  настройкам: `up --republish`.
- **Перехват в расширении не срабатывает** — проверьте `extensions` в `stand.config.json` и журнал
  регистрации базы стенда.
- **Конфигурация на БСП показывает при первом входе «Информационная база перемещена»** — ответьте
  на него один раз в `beforeAll` (образец — в `_hooks.mjs`).
- **Мутирующие сценарии зависят от данных** — гоняйте с `-- --reload-data` (так делает `allure.mjs run`)
  и создавайте в сценарии свой документ, а не правьте общий.
