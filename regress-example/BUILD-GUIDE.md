# Построение регресса прикладного решения по образцу

Инструкция для агента: как по этому примеру построить регресс для решения в другом проекте. Что есть в
примере и как он устроен — [README.md](README.md); дисциплина сценариев и API —
`web-test/regress.md` и `web-test/SKILL.md` в каталоге навыков проекта (`.claude/skills/`,
`.cursor/skills/`, `.codex/skills/` — у каждой платформы свой). Прочитай эти три документа до начала.
Команды `run.mjs start / exec / test` в шагах ниже — команды навыка web-test: вызывай их так, как
описано в его SKILL.md.

Предусловие — web-test настроен (раздел Setup в его SKILL.md). Если `run.mjs` падает с
`Cannot find package 'playwright'`, установка не сделана — это не дефект стенда.

## Порядок

1. **Каркас.** Скопируй `tests/app/` (без `.cache/`, `.artifacts/` и скриншотов ошибок `*.png`) в
   `tests/<приложение>/` проекта.
   Не копируй `seed/` и `etalon/` — они только для примера. Удали `00-smoke/` и `01-*/` после того, как
   напишешь свои сценарии по их образцу.
   Стенд рассчитан на Windows: навыки вызываются через `.ps1` в `powershell.exe`. Если проект не на
   Windows, не адаптируй молча — скажи пользователю, что нужно переделать `execSkill` и публикацию
   (README, «Быстрый старт»).
2. **Настройки стенда** — `stand.config.json`. Данные бери из `.v8-project.json` проекта и у
   пользователя, не придумывай:
   - `v8path` — путь к `1cv8.exe` платформы базы; `label` — имя стенда в реестре пользователя;
   - `user` — администратор базы. Спроси, есть ли у него пароль: основной путь — без пароля в эталоне
     (служебный пользователь или пароль снят на копии); иначе пароль — в переменной
     `REGRESS_STAND_PASSWORD`, не в файлах (README, «Пользователи и пароли»);
   - `cfSrc` — исходники конфигурации; `cfeSrc` — папка, в которой лежат папки расширений (не папка
     одного расширения); `standBase` — `base/stand`;
   - `dtPath` — эталон вне git, например `base/checkpoints/<имя>.dt`;
   - `port` — свободный, не занятый другими публикациями; `apachePath` — `tools/apache24` проекта;
   - убери `skillsRoots`, если навыки лежат в каталоге платформы в проекте (`.claude/skills`,
     `.cursor/skills`, `.codex/skills` и др. — стенд проверяет все);
   - `publications` — по публикации на роль, которая участвует в сценариях; роли и пользователей
     уточни у пользователя;
   - `extensions` — для расширений с перехватами модулей объектов: `{ "<Name>": { "safeMode": "off" } }`,
     ключ — `Name` из `Configuration.xml` расширения, не имя папки.
   Порт и публикации задаются только здесь — `webtest.config.mjs` берёт их отсюда.
3. **Эталон.** Спроси пользователя, из какой базы брать данные (рабочая копия, разведочная база,
   готовый `.dt`). Исходники должны быть закоммичены. Собери:
   `node tests/<приложение>/build-etalon.mjs --source <база|.dt> --out <dtPath>`. В исходную базу
   входит `user` из `stand.config.json` (другой — `--user`); пароль, если есть, — `--pwd`, в файлы не
   пиши. Эталон и манифест — вне git.
4. **Подъём.** `node tests/<приложение>/_stand.mjs up`, затем `status` — все публикации отвечают.
   Конфигурация на БСП при первом входе спрашивает «Информационная база перемещена» — раскомментируй
   `beforeAll` в `_hooks.mjs`.
5. **Контексты** — `webtest.config.mjs`: контекст на публикацию (`url: published('<appName>')`),
   латинский id, русский `displayName`.
   `maxContexts` — не больше числа доступных лицензий 1С.
6. **Разведка — обязательна, до кода сценария.** Метаданные — навыками `meta-info`, `form-info`,
   `role-info`; затем живой проход под нужной ролью:
   `run.mjs start http://localhost:<port>/<appName>/ru_RU` → `exec` → `stop`. Сними точные имена
   разделов, команд, полей, кнопок, статусов и тексты сообщений. Не выдумывай идентификаторы.
7. **Сценарии** — по одному, каждый сразу прогоняй (`run.mjs test tests/<приложение>/ --grep=…`).
   Раскладка: `00-smoke/` (вход, ключевой раздел), дальше папка на процесс. Общие шаги процесса —
   в `_<процесс>.mjs` рядом (файлы с `_` раннер тестами не считает).
8. **Полный прогон** со сбросом данных: `node tests/<приложение>/allure.mjs run`. Разбери каждое
   падение до причины. В `_allure/categories.json` первая категория — образец с текстом-заглушкой:
   впиши текст известного дефекта или удали её.

## Правила

- **Тест — спецификация требуемого поведения.** Имя и шаги — утвердительно. Одно поведение — одна
  проверка: после ожидаемого отказа платформы шаг заканчивается (закрой форму без записи), следующее
  поведение начинай с чистого состояния, а не продолжай в отклонённой форме.
- **Проверяй то, что видит пользователь:** причину отказа — в `getFormState().errors.messages`
  (сообщения решения), а не в тексте исключения действия (это окно платформы «Не удалось записать…»);
  доступность — `buttons[].disabled`; статус — значение поля (у поля надписи — в `texts`, не в
  `fields`).
- **Данные.** Мутирующий сценарий создаёт свой документ; общие данные эталона только читает. Запуск
  мутирующих — с `-- --reload-data`.
- **Без пометок о текущем состоянии в тестах** («здесь падает», номера дефектов). Связь с
  требованием — тег `req-*`, известные красные — корзина в `_allure/categories.json` по тексту ошибки.
- **Без ретраев** (`retries: 0`): повтор мутирующего теста идёт по изменённым данным и прячет причину.
- **Не пиши на стенде, где идёт регресс,** во время разведки: разведочные записи ломают сценарии,
  которые считают строки. Разведку с записью — до прогона, после неё — `--reload-data`.
- **Пароли** — не в файлах репозитория: в `.v8-project.json`, переменных окружения или параметре
  команды (`build-etalon --pwd`, как у навыков `db-*`).
- **Падения инфраструктуры** (лицензии, вход, старт клиента) — не повод править тест: смотри стенд
  (`status`, `down`), реестр и журнал регистрации базы стенда.

## Готовность

- [ ] `_stand.mjs up` с нуля и повторно проходит; повторный — за секунды, стадии пропускаются.
- [ ] Правка `src/cf` после коммита догружается без полной загрузки (`partial db-load-git` в логе).
- [ ] Все сценарии зелёные на свежих данных (`allure.mjs run`), отчёт открывается.
- [ ] В репозитории нет паролей и `.dt`; `.gitignore` проекта — по README.
- [ ] README набора в проекте описывает его стенд: роли, публикации, откуда эталон и как его
      пересобрать.
